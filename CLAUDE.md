# LearnOps — rules for every contributor and every Claude Code session

This file is loaded automatically by Claude Code. It applies to all four modules. Module folders
have their own `CLAUDE.md` with module-specific rules; those add to this file and never override it.

**The specification is `docs/PRD.md`. If anything here or in a request conflicts with the PRD, the
PRD wins. Stop and ask instead of guessing.**

## 1. What we are building

Open-source tools that work **beside an unmodified Moodle (4.5 and 5.3) and BigBlueButton**:
- `modules/studio`: Course Studio (PRD §C1)
- `modules/checker`: course checker, role tests, integration harness (§C2)
- `modules/grading`: grading assistant; owner of the model interface (§C3)
- `modules/video`: video pipeline (§C4)
- `libs/`: shared libraries (`lti`, `moodle_ws`, `model_interface`, `contracts`, `media_paths`)
- `contracts/`: JSON Schemas + examples for PRD Part B

Work is delivered as numbered **releases** (PRD Part D). Only work on requirements tagged for the
release you are on, unless the guide says otherwise.

## 2. Non-negotiable rules (PRD §A7). Never break these, even if asked.

1. **Never modify Moodle or BigBlueButton**: no plugins, themes, filters, patches, or edits to their code or database. Connect only through Moodle backup/Restore, Moodle web services, LTI 1.3, a browser (tests), and BigBlueButton's API.
2. Everything must work on **Moodle 4.5 and 5.3**.
3. **No secrets in the repository**: no API keys, tokens or passwords in code, tests, docs, logs or commit messages. Configuration only through environment variables; document new ones in `.env.example` with placeholders.
4. **Test data only.** Never add real learner data, real course content or real recordings.
5. **AI output is always a draft.** Nothing generated by AI reaches learners or Moodle grades without a mentor's approval. Tools never release grades.
6. **All AI calls go through `libs/model_interface`**, and all speech-to-text through its speech interface. No direct provider SDK calls in modules.
7. **Store media as relative paths only**, never full URLs (PRD C-08).
8. **Protected course items** (final project, course feedback, badge and completion criteria) are never generated, changed or duplicated (PRD §B1.4).
9. Every CLI supports `--dry-run`, `--check`, and has a documented undo.
10. Licences: Apache-2.0 for our code; dependencies must be MIT, BSD or Apache-2.0 (LGPL only as an unmodified library). Check before adding one.

## 3. Shared contracts (PRD Part B)

- Anything in `contracts/` or PRD Part B is a **contract** between modules.
- Contracts are **frozen after Release 0**. After that, only additive, optional fields.
- Never change a contract as a side effect of other work. Use the `/contract-change` command, which follows PRD §B.0 (schema, examples, PRD text and every affected module's tests in one pull request, approved by all affected owners and the guide).
- Validate every contract document you read or write against its schema.

## 4. Architecture rules (PRD §A9)

- Contracts first; additive change only; readers ignore unknown fields.
- External dependencies (model provider, speech provider, storage, Moodle) sit behind an adapter in `libs/`. Swapping one is configuration, not code.
- Optional features behind feature flags.
- Identify activities by Moodle `idnumber`, lessons by slug, never by position or display name.
- Shared code lives in `libs/`; never copy code between modules.
- Heavy work (transcoding, transcription, sandboxed checks) runs in worker containers fed by a job queue, never inside a web request (PRD OPS-10).
- Learner role launches are refused by baseline tools (EXT-07). Don't remove that check.

## 5. Stack (fixed; PRD §A10)

Python 3.12 + FastAPI; React + TypeScript (static build); PostgreSQL 16 (one schema per module,
plus `shared`); Docker Compose; Playwright (Python) for browser tests; ffmpeg for media. Do not
introduce another language, framework or database. Ask the guide first if you think one is needed.

## 6. Code standards

- **Python:** type hints everywhere; `ruff` (lint + format); `mypy --strict` on `libs/`; `pytest`; Pydantic models for every contract and API payload.
- **TypeScript:** `strict` mode; ESLint + Prettier; no `any` without a comment explaining why.
- Small functions; clear names; comments explain *why*, not *what*.
- User-facing messages say what happened and what to do next (PRD UI-05). All strings in one place per module.
- Logs: structured JSON; never log secrets, tokens, or file contents.
- Database changes only through versioned, reversible migrations.

## 6a. Workflow: design first, then build

1. **Contracts, then design.** Contracts (PRD Part B) are drafted and cross-reviewed first. Then each
   module gets a design document, `docs/design/<module>.md`, from `docs/design/TEMPLATE.md`. Draft it
   with `/design-doc <module>`. The developer owns it and must be able to explain every section.
2. **Approval gate.** The document goes `Draft` → `In review` (peer reviewer) → `Approved`. **Only the
   guide sets `Approved`.** Feature code for a module starts only when its design document says
   `**Status:** Approved`. Release 0 foundation work (contracts, shared libraries, CI, test data) may
   start earlier.
3. **Build one requirement at a time** with `/implement <requirement id>`: plan, developer's go,
   tests first, implementation, `/preflight`, then a pull request. Do not batch unrelated requirements.
4. Use plan mode for anything larger than a small fix, and have the developer read and approve the plan.
5. Literature and references: AI tools can invent citations. Open and verify every reference before it
   goes into a document or presentation.

## 7. Definition of done (every pull request)

1. The requirement IDs it implements are in the PR title or description (e.g. `FR-S-03`).
2. Tests added or updated; `/preflight` passes (lint, types, tests, contract validation, secret scan).
3. `docs/traceability.md` updated for any added or changed requirement (PRD §E4).
4. README / `.env.example` updated if behaviour or configuration changed.
5. Reviewed and approved by a member of **another** module; the reviewer runs the tests.
6. No contract changed, or changed through `/contract-change`.
7. The module's design document is `Approved`, or the work is Release 0 foundation work the guide has allowed.

## 8. How Claude Code should work in this repo

- **Read before writing.** Read the relevant PRD section, the module's `CLAUDE.md`, and the existing code before proposing changes.
- **Plan first** for anything larger than a small fix: list the files, the requirement IDs, and the tests, then wait for the developer's go.
- **Small steps.** One requirement or one fix per branch and pull request.
- **Prove it works.** Run the tests and show the output; never claim something works without running it.
- **When unsure, ask.** If the PRD is unclear or two rules conflict, stop and ask the developer, who asks the guide. Never invent a requirement or a contract field.
- **Stay in your module.** Change another module or `libs/` only when the task requires it, and say so explicitly in the PR.
- **Never:** commit to `main`; force-push; disable tests or checks to make them pass; edit `.env`; read or print secrets; run `sudo`; install system packages on a host; add MCP servers or new tools without the guide's approval.
- Each developer uses **their own** Claude Code account; never share one.
