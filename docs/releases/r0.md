## Known limitations and dependencies (Course Checker area)

- No Course Checker code exists: the rule engine, the CK-12 extractor, role tests and the harness are
  Release 1. Feature code waits for the design to be `Approved` (root `CLAUDE.md` section 6a).
- Detection of the planted errors is **not measured**: no checker runs on B8.3 yet (PRD C2.7 is Release 1).
- Open guide decisions on the design: CK-02 as an explaining rule (design section 12 item 24), the JSON
  report field names (item 19), and the guide's view of the CK-07/CK-08 split (item 25). The PRD C2.7
  wording (Moodle 5.3 only) is decided; its PRD edit is pull request #259, not merged when this was written.
- Lab-dependent and unverified: every Moodle 5.3 behaviour in the design, the Teacher and Manager
  backup/restore capabilities against the PRD's administrator-only restore, the effective permissions of
  Student and Administrator, and the individual lab account.

**Scope of the Release 1 `moodle_ws` dependency.** The Checker calls `moodle_ws` only for the B4 course
lookup (`core_course_get_courses_by_field`, by course id or shortname) that binds an LTI context to a Moodle
course (PRD B3 course binding). It does **not** use `moodle_ws` to build the B2 course model: the model comes
from a course package or a `.mbz` backup. No other Moodle web-service call is added for the Checker, and this
note changes no contract or LTI code. The later releases that use more of `moodle_ws` (for example Grading)
are listed by their own owners.

**What was checked.** The B4 contract lists `core_course_get_courses_by_field` for "M2 course lookup"
(`contracts/moodle-ws.v1.md`, function table). `libs/moodle_ws` is on `main` (merged by its owner; it is not
assessed here). Not verified: whether the library exposes a course-lookup helper the Checker can call, and the
